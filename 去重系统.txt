# 基于RocksDB与布隆过滤器的高并发持久化去重引擎设计文档

## 1. 设计背景与核心目标

### 1.1 场景描述
构建一个**本地持久化**的去重引擎，用于爬虫或高并发写入场景。需要满足：
- **长期运行**：支持数年持续运行，数据总量达万亿级别。
- **精确去重**：对每个请求的Key进行精确查重。
- **灵活过期**：每个Key携带独立的绝对过期时间（如`当前时间+30天`），支持不同业务定制。
- **高QPS**：需要承受每秒数十万甚至百万级的查询/写入请求。

### 1.2 核心挑战
- **数据量无限增长**：如何避免存储和内存成为瓶颈？
- **过期清理效率**：如何高效清理数万亿条数据中的过期项？
- **查询性能**：如何在巨大数据集中实现微秒级查重？

## 2. 整体架构设计

### 2.1 数据模型：双Column Family (CF) 设计

采用RocksDB作为存储引擎，利用其LSM-Tree结构和有序Key的特性。

| Column Family | Key 结构 | Value | 用途 |
| :--- | :--- | :--- | :--- |
| **`cf_dedup`** | `namespace_hash:u64` + `key_hash:u128` | `expire_at_ms:u64` + `created_at_ms:u64` + `optional_metadata` | **精确查重**：按Key快速查找，判断是否存在及过期时间。 |
| **`cf_expire`** | `expire_at_ms:u64` + `namespace_hash:u64` + `key_hash:u128` | `empty` | **过期扫描**：按过期时间排序，供后台任务高效清理。 |

**关键设计要点**：
1.  **Key编码**：所有整数（`u64`/`u128`）在构造Key的字节数组时，**必须使用大端字节序（`.to_be_bytes()`）**。这保证了字节的字典序与数值大小序一致，是范围扫描正确性的基础。
2.  **原子写入**：写入一条数据时，必须通过`WriteBatch`原子性地同时写入`cf_dedup`和`cf_expire`，保证两者数据一致性。
3.  **Hash冲突处理**：Value中必须存储完整的原始Key。查重时，在Hash匹配后，需要进一步比对原始Key，以彻底避免Hash冲突带来的误判。

### 2.2 过期清理机制

**核心策略**：利用`cf_expire`的Key有序性，实现高效的**范围扫描删除**。

- **清理流程**：
    1.  后台任务维护一个`last_cleaned_ts`水位线。
    2.  定期（如每分钟）执行扫描，范围是`[last_cleaned_ts, current_time_ms]`。
    3.  对于扫描到的每个Key，从`cf_dedup`和`cf_expire`中**原子删除**。
    4.  更新`last_cleaned_ts`为本轮扫描的最大时间戳。

- **优势**：扫描是顺序读，在SSD上性能极高；删除操作对在线写入和查询影响可控。
- **注意**：需通过限速或错峰（如低峰期加速）来控制清理操作对业务流量的影响。

## 3. 性能加速层：布隆过滤器 (Bloom Filter)

**目的**：拦截绝大多数（>90%）对不存在的Key的查询，避免高QPS下RocksDB频繁磁盘IO，是支撑高并发查重的核心组件。

### 3.1 集成方式
在RocksDB查询路径前，增加一层内存布隆过滤器。

请求 → 布隆过滤器（判断Key“可能存在”）
├── 不存在 → 直接返回“不重复”（快速路径）
└── 可能存在 → 查询 RocksDB cf_dedup（慢速路径，精确确认）


### 3.2 布隆过滤器的大小设定与动态管理

**核心矛盾**：数据总量无限，但内存有限。

**结论**：布隆过滤器的大小由其**有效生命周期内（即两次重建之间）的预期写入量（n）**决定，而非历史总数据量。

- **大小计算公式**：`m = - (n * ln(P)) / (ln(2)^2)`
    - `m`: 位数组大小（bit）
    - `n`: 重建周期内的预期写入数据条数
    - `P`: 可接受的误判率（推荐0.01，即1%）

- **管理策略：定时全量重建**（推荐）
    1.  **设定重建周期**：例如每24小时，在业务低峰期执行。
    2.  **双缓冲构建**：后台基于`cf_dedup`中**所有未过期数据**，从头构建新的布隆过滤器。构建期间，旧过滤器继续服务。
    3.  **原子切换**：新过滤器构建完成后，原子替换旧过滤器。
    4.  **资源释放**：安全释放旧过滤器内存。

- **应对容量不确定性的机制**：
    - **监控**：持续监控布隆过滤器的**插入量/设计容量**和**实际误判率**。
    - **自动扩容**：当插入量超过容量的80%或误判率超过阈值（如1.5%）时，**自动触发一次应急的全量重建**，并使用更大的容量参数（如扩容1.5倍）。

### 3.3 为什么这个方案能长期运行？

| 挑战 | 解决方案 |
| :--- | :--- |
| **数据总量无限增长** | 通过“定时全量重建”，将有效数据的“视图”限制在一个时间窗口内。 |
| **布隆过滤器内存爆炸** | 内存占用恒定在 `2 * (日增量 * 9.6 bit)` 左右，与总数据量无关。 |
| **过期数据导致误判率升高** | 每次重建时，只包含`cf_dedup`中的有效数据，自动剔除了过期Key。 |

## 4. 关键知识点：字节序（Byte Order）

在构造多字节整数（`u64`/`u128`）的Key时，必须理解字节序对RocksDB排序的影响。

| 概念 | 说明 | 对RocksDB的影响 |
| :--- | :--- | :--- |
| **字典序** | 计算机比较字节数组的方式，从第一个字节开始逐个比较。 | RocksDB正是按此顺序排列所有Key。 |
| **小端字节序** | 数字的**低位字节**存储在内存地址的前端（如`256` -> `[0x00, 0x01, ...]`）。 | 导致数字的字典序与数值序相反（如`256`排在`1`前面），**范围扫描完全失效**。 |
| **大端字节序** | 数字的**高位字节**存储在内存地址的前端（如`256` -> `[0x01, 0x00, ...]`）。 | 保证数字的字典序与数值序完全一致，**是范围扫描正确性的前提**。 |

**工程要求**：在Rust中构造Key时，**必须统一使用`.to_be_bytes()`** 将整数转换为大端字节序。

## 5. 技术选型与权衡

| 组件/策略 | 选型 | 理由 |
| :--- | :--- | :--- |
| **存储引擎** | RocksDB | LSM-Tree架构，写入性能极高；支持Key有序和范围扫描；支持原子WriteBatch。 |
| **内存加速** | 定时重建的布隆过滤器 | 内存开销可控（恒定）；查询性能极高；实现相对简单，与RocksDB解耦。 |
| **过期清理** | 基于`cf_expire`的主动范围扫描 | 清理效率高；对在线流量影响小；实现直观，与业务逻辑独立。 |
| **Key编码** | 大端字节序 | 保证范围扫描正确性，是设计正确运行的基础。 |

## 6. 后续演进与优化方向

1.  **布隆过滤器重建优化**：研究更快的全量遍历方法（如并行扫描RocksDB），缩短重建时间。
2.  **分层布隆过滤器**：如果单次全量重建仍然太慢，可考虑“热数据”+“冷数据”的多层过滤器设计，进一步降低重建频率和内存占用。
3.  **清理任务调度**：精细化后台过期清理任务，实现基于负载的**自适应限速**，在业务高峰期完全暂停，低峰期全速运行。
4.  **监控与告警体系**：建立完善的Dashboard，监控布隆过滤器命中率、RocksDB读写延迟、过期数据积压量等关键指标。
